# 01. 系統架構設計與演進文件 (System Architecture)

**專案名稱**：小灶私廚 — 訂單管理系統
**最近更新**：加入 GAS 中介層、UUID 架構重構與並發效能最佳化

## 一、系統定位與發展背景
本系統專為「小灶私廚」打造，提供跨平台的輕量級訂單與排單管理工具。為達成「無縫雙人協作」、「低成本營運」與「免去開發環境依賴」等目標，本系統全面揚棄了傳統關聯式的後端資料庫，直接以 **Google Sheets (Google 試算表)** 作為資料庫（Backend DB）。

## 二、基礎架構：從 OAuth 到 GAS 中介層的演進
系統架構隨著實務需求，經歷了重要的一次迭代升級：

### 1. 初版架構（前端直連）
- **機制**：前端 JavaScript 直接透過 Google Sheets API 取用 Oauth 2.0 Token 對資料表進行互動。
- **痛點**：強制要求每次使用皆須先進行 Google 登入授權，且 Token 會過期，導致使用者體驗瑣碎，且無法「打開即用」。

### 2. 現行架構（導入 Google Apps Script API 中介層）
- **機制**：前端純做靜態 SPA (Single Page Application)，並建立一支由 Google Apps Script (GAS) 代管的後端 API 端點 (`Backend.gs`) 作為緩衝層。
- **優勢**：
  - **極致便利**：使用者無須再頻繁授權登入，如同原生 APP 般「隨插即用」。
  - **安全性提升**：隱藏了試算表的真實存取權限與 ID，不需將憑證暴露在前端。

## 三、模組與設計理念 (Design Philosophy)

1. **靜態網頁與響應式開發 (RWD)**
   前端採 Vanilla JS 與傳統 CSS 開發，所有樣式經過彈性排版 (`Flexbox`/`Grid`) 以及適應手機寬度的自定義樣式 (`vh/vw`, `media queries`)，確保管理者能在狹小螢幕的手機上依然能快速點選、滑動甚至檢視統計圖表。
   針對瀏覽器常有的快取 (Cache) 卡死問題，專案在 HTML 引用端支援了帶版本號的強制更新機制（例：`script.js?v=2`）。

2. **多模組分工 (Modular Pattern)**
   所有的業務領域採單例模式（Module Pattern），將邏輯封裝隔離（例如：`OrderNew`, `OrderList`, `MenuMgmt`, `Revenue`），統一由 `App.js` 管理路由與分頁的顯示隱藏。

3. **效能最佳化：非同步並發 (Promise.all)**
   對 GAS 的網路請求具有物理時間延遲，若採順序執行將嚴重拖慢體驗。因此，前端在處理包含大量跨表寫入操作時（例如訂單存檔需同時寫入「訂單主檔」與多筆「排單表」），已全面改寫為 `Promise.all` 結構，達成多任務平行發佈，將等候時間壓縮至極致（最高帶來 2~3 倍的儲存加速）。

## 四、風險防禦機制

- **UUID 全域唯一識別碼綁定**：過去依賴資料列行號 (Row Index) 的變更方式會導致多人協作時的覆蓋或錯頻，全面導入 UUID 讓每一筆資料都是絕對唯一的實體。
- **防止髒資料與手誤干擾（Trim 容錯器）**：透過在讀取欄位名稱或是品項字串時強制套用空白過濾機制（`.trim()`），化解在試算表上因手滑造成的標題空白偏移錯亂問題（例如：`訂購數量 `）。
